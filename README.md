# README

## Проект
**Кейс 8. Библиотека: выдача и просрочки**

Проект посвящён разработке базового АБИС-контура для библиотеки с учётом каталога книг (изданий и экземпляров), читателей, выдач, возвратов и просрочек. Основная цель — снизить долю просроченных выдач и повысить оборачиваемость книжного фонда. В версии 0.2 добавлены многоэкземплярность каталога и авторизация читателей с личным кабинетом.

Проект выполняется как **гибридное решение**:
- **1С:Предприятие 8.3** — основная бизнес-логика, справочники, документ «Выдача/Возврат», регистр выдач, отчётность и HTTP-сервис для сайта;
- **сайт (UI + бэк)** — пользовательские сценарии: каталог, вход читателя и личный кабинет с историей выдач;
- **CSV / JSON** — импорт, тестовые данные и выгрузка результатов.

---

## Бизнес-цель
- снизить просрочки возврата;
- повысить оборот фонда;
- сократить время ожидания популярных книг;
- упростить контроль задолженностей;
- повысить прозрачность статистики использования фонда;
- дать читателю удобный доступ к своей истории выдач через личный кабинет.

Целевой ориентир проекта: **снижение доли просроченных выдач до ≤ 3% на тестовом наборе T1**.

## Основные сущности

Логическая схема данных:
- `books (book_code, title, author, year, udk)` — издание (библиографическая запись);
- `copies (copy_code, book_code, status)` — физический экземпляр издания;
- `readers (reader_id, fio, group, login, password_hash)` — справочник читателей;
- `loans (loan_id, reader_id, copy_code, issue_date, due_date, return_date)` — учёт выдач и возвратов.

Реализация в 1С (фактические объекты):
- `Справочник.Книги` — издание: `Наименование`, `Автор`, `ГодИздания`, `УДК`;
- `Справочник.Экземпляры` (подчинён `Книги`) — `Код` (инв. номер), `Владелец` → Книги, `Состояние`;
- `Справочник.Читатели` — `Наименование` (ФИО), `Группа`, `Пол`, `Логин`, `ХешПароля`;
- `Документ.ВыдачаКниг` — `Читатель`, `Экземпляр`, `ДатаВыдачи`, `ДатаВозвратаПлан`, `ДатаВозвратаФакт`;
- `РегистрСведений.Выдачи` — измерения `ДокументВыдачи`, `Экземпляр`, `Читатель`.

## Основные бизнес-правила
1. **Издания и экземпляры.**
   `Справочник.Книги` — это издание (название, автор, год, УДК). `Справочник.Экземпляры` (подчинён изданию) — физические копии с инвентарным номером и состоянием. У одного издания может быть несколько экземпляров.

2. **Один экземпляр — одна активная выдача.**
   На один экземпляр в каждый момент времени может приходиться не более одной активной выдачи.

3. **Жизненный цикл выдачи.**
   - выдача оформляется на конкретный экземпляр, фиксируются `issue_date` и `due_date`, экземпляр переходит в состояние «Выдан»;
   - при возврате фиксируется `return_date`, экземпляр возвращается в «Доступен».

4. **Определение просрочки.**
   Выдача считается просроченной, если `return_date = NULL` и текущая дата больше `due_date`, либо `return_date > due_date`.

5. **Проверка дат.**
   `issue_date ≤ due_date`; если возврат указан, то `due_date ≤ return_date`.

6. **Ссылочная целостность.**
   Значения `reader_id` и `copy_code` должны существовать в соответствующих справочниках.

7. **Повторная выдача экземпляра запрещена**, пока предыдущая выдача не закрыта.

8. **Авторизация читателя.**
   Логин и пароль выдаёт библиотекарь вручную через 1С при регистрации. Пароль хранится только в виде хеша с солью. Авторизованный читатель видит только свою историю выдач.

## KPI и отчётность
Ключевой отчёт проекта — **«Просрочки»**.

### Поля отчёта
- `reader_id`
- `fio`
- `copy_code`
- `title`
- `days_overdue`

### Показатели
- доля просроченных выдач;
- средняя просрочка в днях;
- медианная просрочка в днях;
- TOP-N читателей по просрочкам;
- TOP-N книг по просрочкам.

### Фильтры отчёта
- период;
- группа читателя;
- автор / UDK;
- интервал просрочки.

### Экспорт
Обязателен экспорт отчёта в CSV минимум с полями:
- `reader_id`
- `copy_code`
- `days_overdue`

## Авторизация читателя (личный кабинет)

Доступ к 1С извне — только через сайт. Сайт обращается к 1С по HTTP-сервису `БиблиотекаAPI` с сервисной учётной записью; проверка пользователя идёт по хешу пароля.

Основные потоки:
- **Вход:** браузер → бэк сайта (логин/пароль) → 1С (`POST /library/auth/verify`, проверка по хешу) → бэк выпускает сессионный токен → cookie в браузере.
- **Мои книги:** браузер (cookie) → бэк проверяет сессию локально → 1С (`GET /library/loans?reader=<id>&status=...`) → история выдач читателя.
- **Выход:** сессия завершается на бэке; в 1С ничего не отправляется.

Регистрация, восстановление и смена пароля выполняются только библиотекарем в 1С — самостоятельной регистрации через сайт нет.

## Ролевая модель
### Читатель
- авторизуется на сайте (логин/пароль выдаёт библиотекарь);
- поиск книги в каталоге;
- просмотр своей истории выдач и сроков в личном кабинете;
- получение информации о просрочке.

### Библиотекарь
- регистрация читателя и выдача ему логина/пароля;
- проверка данных читателя и книги;
- оформление выдачи на конкретный экземпляр;
- оформление возврата;
- фиксация просрочек;
- обновление состояний экземпляров и статусов выдач.

### Администратор
- просмотр отчётов;
- контроль просрочек;
- настройка доступа;
- ведение справочников и контроль системы.

## Нефункциональные требования
- построение отчёта по набору не менее **100 выдач** должно выполняться интерактивно;
- импорт CSV должен быть **идемпотентным**;
- в системе должен вестись **журнал изменений по выдачам**;
- роли пользователей должны быть разделены по функциям;
- доступ к 1С извне — только через сайт (сервисная учётная запись); пароль хранится в виде хеша; пользовательская сессия ограничена по времени.

---

## Ограничения проекта
- проект учебный;
- используются только синтетические данные;
- интеграции с внешними библиотечными системами отсутствуют;
- официальные открытые датасеты допускаются только как дополнение к справочной информации по книгам;
- данные о выдачах формируются внутри учебного контура;
- доступ к 1С извне возможен только через сайт.

---

## Риски и допущения
- **нет реальных данных** → используется синтетический набор;
- **сложность UI** → делается прототип, а не полнофункциональная боевая система;
- **неполные требования** → границы MVP фиксируются заранее;
- **нет доступа к АБИС** → решение проектируется без внешних интеграций;
- **безопасность доступа** → хеш пароля с солью, доступ к 1С только через сайт, ограниченное время сессии;
- **лимит сессий 1С** → сайт обращается к 1С только за данными, проверка входа выполняется на бэке.

## Как проверять проект
### Проверка документации
1. Открыть `Карточка_проекта_v0.2.md` и проверить бизнес-цель, команду, MVP и план.
2. Открыть `bpmn.png` и проверить сценарий выдачи / возврата (шлюз «есть свободный экземпляр»).
3. Открыть `dfd_1.png` и проверить потоки данных, включая хранилище «Экземпляры».
4. Открыть `ERD-2.png` и проверить связи Книги → Экземпляры → ВыдачаКниг.
5. Открыть `idef0_1.jpg` и `idef0_2.jpg` и проверить контекст и декомпозицию.
6. Открыть `Авторизация_читателей.html` и проверить сценарии входа.

### Проверка логики проекта
1. В справочниках должны существовать издания, экземпляры и читатели.
2. У одного издания может быть несколько экземпляров.
3. При выдаче книги выдача оформляется на конкретный экземпляр, создаётся запись в `loans`, состояние экземпляра меняется на «Выдан».
4. Нельзя выдать занятый экземпляр повторно, пока предыдущая выдача не закрыта.
5. При возврате фиксируется `return_date`, экземпляр возвращается в «Доступен».
6. При нарушении срока возврата запись попадает в отчёт «Просрочки».
7. Отчёт экспортируется в CSV.
8. Читатель авторизуется на сайте и видит только свою историю выдач.

### Проверка тестового набора
1. Набор содержит не менее 100 выдач.
2. В данных должны быть:
   - издания с несколькими экземплярами;
   - активные выдачи;
   - закрытые выдачи;
   - просроченные выдачи;
   - корректные и граничные случаи по датам.
